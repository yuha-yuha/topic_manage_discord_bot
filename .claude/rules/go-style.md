# Go コーディング規約

## 基本

- `gofmt` / `goimports` で整形済みであること。
- [Effective Go](https://go.dev/doc/effective_go) と [Go Code Review Comments](https://go.dev/wiki/CodeReviewComments) に従う。
- import は「標準ライブラリ」「外部パッケージ」「自リポジトリ内パッケージ」の 3 グループに空行で分ける。

## 命名

- パッケージ名は小文字の単語 1 つ。`util` / `common` / `helper` のような汎用名は避ける。
- パッケージ名と重複する命名をしない（`user.UserService` ではなく `user.Service`）。
- 略語は大文字で統一する（`ID`, `URL`, `HTTP`。`Id`, `Url` は不可）。
- レシーバ名は 1〜2 文字の短い名前で、同じ型では統一する。`this` / `self` は使わない。

## エラーハンドリング

- エラーは必ず処理する。`_` で握りつぶす場合は理由をコメントで残す。
- 上位に返すときは `fmt.Errorf("...: %w", err)` で文脈を付けてラップする。
- エラーメッセージは小文字始まり、末尾に句読点を付けない。
- 判定は `errors.Is` / `errors.As` を使い、文字列比較はしない。
- `panic` はプログラムの初期化失敗など回復不能な場合に限る。

## context

- I/O を伴う関数・リクエストスコープの処理は第 1 引数に `ctx context.Context` を取る。
- `context.Context` を構造体のフィールドに保持しない。

## インターフェース

- インターフェースは「使う側」のパッケージで定義する（例: `service` が必要とする repository のインターフェースは `service` に置く）。
- 必要なメソッドだけを持つ小さなインターフェースにする。
- 関数は「インターフェースを受け取り、具体型を返す」。

## その他

- グローバル変数による状態共有をしない。依存はコンストラクタ（`NewXxx`）で注入する。
- `init()` は原則使わない。
- エクスポートする識別子には、識別子名で始まる doc コメントを付ける。
